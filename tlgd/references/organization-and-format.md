# Organization and format

## Pages, headings, and paragraphs

- Give each page one unique level-1 heading that states its primary purpose.
- Use sentence case. Start task headings with a base-form verb and conceptual headings with a noun phrase. Avoid opening with an *-ing* form when a clearer alternative exists.
- Prefix a section that is not required for every reader with **Optional:**.
- Keep headings descriptive, concise, and unique. Limit punctuation and abbreviations. Do not put links in headings, number headings to imply sequence, or skip hierarchy levels.
- Avoid code in headings. If code is necessary, add a descriptive noun and use code formatting where the publishing system supports it.
- Put content after every heading. Introduce a group of subsections with **the following sections**, not ambiguous **this section**.
- Put the paragraph's critical information first. Keep each paragraph focused and use shorter sentences and paragraphs.
- Do not force line breaks inside prose. Let the renderer reflow text for different windows, devices, and text sizes.

## Lists

- Use a numbered list when sequence or priority matters, a bulleted list for unordered items, and a description list for term-description pairs.
- Do not create a list for one item. Make it clear whether readers need every unordered item or can choose among them.
- Introduce a list with a complete sentence when context is needed. Do not make the items complete an introductory fragment.
- Keep items parallel. Start each with a capital letter.
- End an item with punctuation when it contains a verb or a complete thought. Omit punctuation for a single word, a verb-free fragment, code-only content, a link, or a document title.
- If punctuation becomes inconsistent, rewrite for parallelism or punctuate every item.
- For a run-in heading, use bold and a period or colon consistently. Do not use a dash between the heading and description.
- In an inline series, use the serial comma and introduce nonexhaustive examples instead of ending with **etc.**

## Tables

- Use a table for genuinely two-dimensional comparison. Use a list for one column, a description list for simple pairs, and prose for a single item.
- Never use a table for page layout, code layout, a multicolumn one-dimensional list, or—when avoidable—the middle of a procedure.
- Introduce the table with a complete sentence and place it next to the relevant prose.
- Use sentence case and concise column headings without end punctuation. Mark row and column headers with `th` and appropriate `scope`.
- Do not use styling alone to indicate headers. Do not merge cells or convey information only through color, an icon, or an image.
- Order rows logically or alphabetically. Split a complex table rather than forcing multiple header layers.
- Caption nearby tables when readers need to distinguish them. Use **Table NUMBER. DESCRIPTION** and refer to a numbered table in lowercase.
- Ensure the table works at narrow viewport widths and for screen readers.

## Notices and footnotes

- Use notices sparingly because readers often skip them. Do not stack notices.
- Use a note only for relevant but nonessential information that is outside the main flow.
- Do not put prerequisites, required steps, expected results, ordinary cross-references, or information required for success in a note.
- Use a caution when the reader must proceed carefully and a warning for risk of harm, data loss, or an irreversible action. Use a success notice only where the interactive format supports it.
- Prefer inline text, a cross-reference, a notice, or a parenthetical over a footnote. If a footnote is unavoidable, use a superscript number rather than a symbol.

## Visual text formatting

- Use bold for named UI elements and run-in headings, including notice labels. Do not use bold as generic emphasis.
- Use italics sparingly for a term being introduced, a word discussed as a word, a variable, a version variable, a full-length work, or real emphasis.
- Reserve underlining for links.
- Use code formatting for code-related text and literal input. Use semantic Markdown or HTML rather than manually changing font family, size, or color.
- Keep formatting consistent for equivalent elements and do not make appearance carry meaning by itself.

## Introduce examples

- Use **such as**, **for example**, or **like** according to the sentence.
- At the end of a sentence, introduce an example with a comma or em dash when grammatically appropriate.
- Keep a short parenthetical example short. Move a long example to the end or give it its own sentence or block.
